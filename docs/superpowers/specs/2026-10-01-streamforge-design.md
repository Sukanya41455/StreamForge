# StreamForge Design

**Purpose:** A local, demonstrable real-time marketplace analytics platform that teaches and evidences backend, data, and platform-engineering fundamentals for interviews.

## Success criteria

- `docker compose up --build` runs a producer, Kafka, Spark Structured Streaming, PostgreSQL, FastAPI, Prometheus, and Grafana on one machine.
- A normal scenario produces orders and payments; the API returns minute-level revenue, payment success rate, and rolling top products.
- Duplicate, late, and elevated failure-rate scenarios visibly affect the appropriate metrics without corrupting aggregates.
- Restarting the streaming job resumes from its checkpoint; a documented failure experiment records the observed result.
- A `kind` deployment can run the workload locally, expose the API, and demonstrate API HPA behavior.
- The README contains exact start commands, architecture, dashboard screenshots/results placeholders, and interview talking points grounded in measured results only.

## Constraints

- Entirely local and free; no cloud account or managed service.
- Use Python for producer, API, and test tooling; Kafka, PySpark Structured Streaming, PostgreSQL, Docker Compose, Prometheus, Grafana, Kubernetes, and `kind` are in scope.
- Keep the first runnable system small: one Kafka broker, one Spark streaming process, and one PostgreSQL instance. A three-broker topology is a documented scaling exercise, not a prerequisite.
- No invented benchmark figures. Measurements are generated by scripts and recorded in `docs/benchmarks.md`.

## Architecture

```text
producer ──raw.orders / raw.payments──> Kafka ──> Spark processor ──> PostgreSQL
                                                   │                    │
                                                   └─ app metrics ─────> FastAPI
                                                                            │
Prometheus <── /metrics from producer, processor, API <────────────────────┘
      │
Grafana dashboards and alerts
```

The producer emits versioned JSON records with a stable `event_id`, event timestamp, and scenario controls. Spark owns validation, a dead-letter output, event-time watermarking, and duplicate suppression. It writes queryable aggregates to PostgreSQL through idempotent upserts. FastAPI is read-only: it serves persisted results and metrics rather than consuming Kafka itself.

## Event and storage contract

`OrderEvent`: `event_id`, `order_id`, `user_id`, `product_id`, `amount`, `region`, `event_time`.

`PaymentEvent`: `event_id`, `payment_id`, `order_id`, `status` (`succeeded` or `failed`), `amount`, `event_time`.

Kafka topics: `streamforge.orders.v1`, `streamforge.payments.v1`, and `streamforge.dead-letter.v1`.

PostgreSQL tables: `minute_metrics` (revenue/order/payment aggregates), `product_window_metrics` (rolling top products), and `stream_errors` (invalid-message evidence). Composite primary keys include window boundaries so replay/upsert is safe.

## Delivery phases

1. Repository, event contracts, deterministic producer, and tests.
2. Dockerized Kafka/PostgreSQL plus a consumer smoke test.
3. Spark transformations with watermarks, deduplication, and Postgres aggregate sink.
4. FastAPI query surface and Prometheus instrumentation.
5. Compose-operated full stack plus Grafana dashboard and alerts.
6. Load/fault scripts with a reproducible result template.
7. Local `kind` manifests, health probes, resource limits, and API HPA demonstration.

## Deliberate non-goals

- Cloud deployment, multi-region replication, authentication/authorization, a web frontend, production credentials management, and exactly-once claims.
- ClickHouse is deferred: PostgreSQL keeps the first system focused. An optional migration comparison is documented only after the core results exist.

## Verification strategy

Unit tests cover event validation, scenario generation, transformation semantics, aggregate upserts, and API responses. Compose smoke tests prove messages cross the Kafka boundary and data reaches PostgreSQL. Failure scripts preserve artifacts describing input rate, component killed, recovery time, consumer lag, and observed data behavior. Kubernetes smoke checks validate readiness, service access, and HPA scale decisions.

## Interview narrative

The project demonstrates the difference between at-least-once delivery and idempotent effects, partitions/offsets versus consumer groups, event time versus processing time, watermark trade-offs, state/checkpoint recovery, consumer lag/backpressure, observability signals, and the limits of CPU-based autoscaling. Every claim in the README links to a reproducible command or recorded experiment.
